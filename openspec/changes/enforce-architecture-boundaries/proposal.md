## Why

The July 2026 repository assessment found that `:core:network` is not a pure transport module and that features depend on concrete adapters instead of domain ports, contradicting the architecture decisions adopted in `docs/superpowers/plans/2026-07-23-repository-assessment-remediation.md` ("Architecture boundary," decision 3-4). Verified against the current tree:

- `core/network/build.gradle.kts:11-12` declares `implementation(project(":core:database"))` and `implementation(project(":core:preferences"))`. `core/network/src/commonMain/kotlin/net/subsloth/core/network/media/CatalogRepository.kt` is a repository/orchestration class living inside the transport module: its constructor takes `api`, `catalogDao` (a `:core:database` DAO), and `userPreferences` (a `:core:preferences` type); its doc comment describes it as coordinating "API fetching, Room database caching, and DataStore timestamp tracking." This is exactly the kind of class the plan's `:core:data` decision targets — currently misplaced.
- `core/network/src/commonMain/kotlin/net/subsloth/core/network/error/UiErrorMapping.kt` defines `toUiError()` extension functions consumed by `feature/details/src/commonMain/kotlin/net/subsloth/details/DetailViewModels.kt:24`. UI-facing error mapping lives in the transport module rather than a UI-facing module.
- `feature/auth/src/commonMain/kotlin/net/subsloth/auth/LoginViewModel.kt:22,58,65` imports `net.subsloth.preferences.UserPreferences` directly (for `UserPreferences.DEFAULT_API_BASE_URL`) — a feature ViewModel referencing a concrete adapter type, not a domain port.
- `feature/catalog`, `feature/details`, `feature/player` declare a `project(":core:network")` dependency in `build.gradle.kts`; `feature/library` and `feature/settings` declare `project(":core:database")`/`project(":core:preferences")` dependencies. Source-level grep found zero imports of any concrete adapter package inside `feature/catalog`, `feature/library`, `feature/player`, or `feature/settings` — these modules' ViewModels consume only `:core:domain`/`:core:model` types, so the build-graph edges to concrete adapter modules are currently unused and removable without source changes.
- `core/model/build.gradle.kts:8-10` declares `api(libs.compose.runtime)` so 17 files can use `@Stable`/`@Immutable`. The canonical `architecture` spec's "Functional Core Boundary" requirement currently states core modules SHALL have no Compose dependency, which `:core:model` already contradicts — a spec/implementation conflict this change must resolve one way or the other.
- The existing `CoreModelArchitectureTest` and `DomainArchitectureTest` (in `core/model`/`core/domain` `jvmTest`) only walk `commonMain` source files and regex-match `import` lines; they do not inspect the resolved Gradle dependency graph, so a transitively-pulled dependency with no matching import string would pass undetected, and they cannot see `androidMain`/`jvmMain`/`wasmJsMain` violations. `NetworkPolicyTest` is a separate, valid test of network API/policy (Ktor plugin wiring, reflection-based field/endpoint checks) — it is not an architecture-boundary test and is out of this change's scope.
- `webApp/build.gradle.kts:3-8` applies no `subsloth.*` convention plugin — it is the only app/library module in the repo that doesn't. Since Spotless/Detekt are configured per-convention-plugin (not applied repo-wide from the root `build.gradle.kts`), `:webApp` currently receives zero Spotless or Detekt coverage.
- Composition-root construction is undocumented and inconsistent: `androidApp/src/main/java/net/subsloth/AppContainer.kt` is a manual service locator that constructs real `Api`/`ClientFactory`, Room `SubSlothDatabase`, `DataStore<Preferences>`/`UserPreferences`, and the concrete `CatalogRepository`. `desktopApp`/`webApp` construct no adapters at all — both fall back to `core/ui/src/commonMain/kotlin/net/subsloth/core/ui/RootContainerViewModel.kt`'s in-memory `SessionPort` default, which its own doc comment says is "suitable for the screenshot suite and dev/demo build flavours," not production.

## What Changes

- Add a new `:core:data` module (KMP library, `subsloth.kmp.library` convention) depending on `:core:model`, `:core:domain`, `:core:network`, `:core:database`, `:core:preferences`. Move `CatalogRepository` from `:core:network` into `:core:data`.
- Remove `:core:database`/`:core:preferences` dependencies from `core/network/build.gradle.kts`. `:core:network` retains only `Api`/`ClientFactory`/`CatalogPortAdapter` and DTO-to-domain mapping — pure HTTP transport.
- Move `UiErrorMapping.kt`'s `toUiError()` functions from `:core:network` into `:core:ui`, and update `feature/details`'s import accordingly.
- Move `UserPreferences.DEFAULT_API_BASE_URL` (or an equivalent default-base-URL constant) to `:core:domain`/`:core:model` so `feature/auth`'s `LoginViewModel` no longer imports `net.subsloth.preferences.UserPreferences`.
- Remove the now-unused `project(":core:network")` dependency from `feature/catalog`, `feature/details` (after the `toUiError` move), and `feature/player`; remove the unused `project(":core:database")`/`project(":core:preferences")` dependencies from `feature/library` and `feature/settings`. Add `project(":core:data")` only where a feature's composition wiring genuinely needs it (expected: none — features depend on `:core:domain` ports only; concrete `:core:data`/`:core:network`/`:core:database`/`:core:preferences` wiring happens at each app's composition root).
- Attempt to remove the Compose runtime dependency from `:core:model` by replacing its `@Stable`/`@Immutable` annotations with a Compose stability configuration file consumed by Compose-applying modules (`:core:ui`, `feature:*`, the three app modules). If this proves technically unsound during implementation, keep the dependency and instead add a narrow, justified exception to the `architecture` spec's "Functional Core Boundary" requirement, documenting exactly why.
- Add a Gradle dependency-graph invariant test (new JVM test consuming the Gradle `Project`/configuration API, not source-import scanning) that fails when any `feature/*` module declares a dependency on `:core:network`, `:core:database`, `:core:preferences`, or `:core:data`, or when `:core:network` declares a dependency on `:core:database`/`:core:preferences`. (`:core:media` is a shared playback/UI module, not a concrete adapter, and remains permitted.) Covers the six `feature/*` modules and `:core:network` — the modules this change defines forbidden edges for — checked across both of their declared Kotlin targets (`jvm`, `wasmJs`), not just `commonMain`.
- Add a `subsloth.web.library` convention plugin (mirroring `subsloth.jvm.library`) applying Spotless and Detekt with the same configuration as other convention plugins; migrate `webApp/build.gradle.kts` to use it instead of raw `kotlin("multiplatform")` plus raw plugin aliases.
- Document composition-root ownership (which module/class is responsible for constructing real adapters on each platform, and that `RootContainerViewModel`'s in-memory default is a non-production fallback) in a new doc referenced from `docs/agent/README.md`.
- Update `openspec/specs/project/spec.md`'s "Android Project Baseline" and "Repository Scaffold Layout" requirements to include `:core:data` in the listed modules.

## Capabilities

### Modified Capabilities

- `architecture`: `:core:network` no longer owns persistence/preferences; UI error mapping moves to a UI-facing module; either `:core:model` sheds its Compose dependency or the boundary rule gains a narrow documented exception; architecture tests become real dependency-graph invariants covering every source set.
- `project`: module list gains `:core:data`; convention-plugin discipline is extended to `:webApp` via a new `subsloth.web.library` plugin.

## Impact

- Affects `core/network`, new `core/data`, `core/model`, `core/ui`, `feature/auth`, `feature/catalog`, `feature/details`, `feature/library`, `feature/player`, `feature/settings`, `webApp`, `build-logic/convention`, `settings.gradle.kts`, and composition-root construction is documented (not rewired — Android's `AppContainer` keeps constructing `CatalogRepository`, now imported from `:core:data` instead of `:core:network`; Desktop/Web composition-root wiring itself is Changes 3A/3B's scope, not this one).
- No user-facing behavior change; this is a structural/dependency-graph refactor. Existing tests must continue to pass; `CatalogRepository`'s tests move with it to `:core:data`.
- Risk: medium. Moving `CatalogRepository` and its tests, and potentially removing `:core:model`'s Compose dependency, touch real production code across several modules and must keep the full test suite green. The Compose-stability-config removal is the highest-uncertainty item; it has an explicit fallback (document the exception instead) so it cannot block the rest of the change.
