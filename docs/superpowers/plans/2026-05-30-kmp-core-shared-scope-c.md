# KMP Core Shared Scope C (Shared Data Layer) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert `:core:database` and `:core:preferences` from Android-only libraries to KMP libraries, replacing Room with SQLDelight and DataStore Preferences with multiplatform-settings.

**Architecture:** The database and preferences modules are the persistence layer of the imperative shell. Room and DataStore are Android-only. SQLDelight generates KMP-compatible type-safe Kotlin from SQL, and `multiplatform-settings` provides a simple key-value store for all platforms. The DAOs, entities, and preference stores need rewriting; the domain ports they implement stay unchanged.

**Tech Stack:** SQLDelight 2.x (multiplatform SQL database), multiplatform-settings (multiplatform key-value store), kotlinx-serialization-json. Kept: kotlinx-datetime, kotlinx-collections-immutable.

**Scope boundary:** Only `:core:database` and `:core:preferences` change. All downstream Android modules (`:core:media`, `:feature:*`, `:app`) stay unchanged. `:core:model` and `:core:domain` are already KMP from Scope A. `:core:network` is already KMP from Scope B.

---

## Migration Strategy

| Current | KMP Replacement |
|---|---|
| Room `@Entity`, `@Dao`, `@Database` annotations | SQLDelight `.sq` schema files, generated Kotlin types |
| Room `@Insert`, `@Query`, `@Delete` | SQLDelight generated queries from `.sq` files |
| Room `RoomDatabase` abstract class | SQLDelight `SqlDriver` (Android: `AndroidSqliteDriver`, Native: `NativeSqliteDriver`) |
| Room Flow DAOs return `Flow<List<T>>` | SQLDelight `.asFlow().mapToList()` |
| DataStore `<Preferences>` | `multiplatform-settings` `Settings` |
| DataStore `edit { }` / `updateData { }` | `Settings.putString()`, `Settings.putInt()`, etc. |
| DataStore Flow-based reads | `Settings` has no Flow — wrap in `MutableStateFlow` or `channelFlow` |

### SQLDelight schema migration

The Room entities contain 11 tables. Each needs a `CREATE TABLE` in the `.sq` file and corresponding queries.

The `.sq` file structure:

```sql
-- SubSlothDatabase.sq

-- Account-scoped tables

CREATE TABLE cached_online_metadata (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    profileKey TEXT NOT NULL,
    contentId TEXT NOT NULL,
    contentType TEXT NOT NULL,
    title TEXT NOT NULL,
    overview TEXT,
    posterUrl TEXT,
    backdropUrl TEXT,
    year INTEGER,
    genres TEXT,
    runtime INTEGER,
    rating REAL,
    cachedAtEpochSeconds INTEGER NOT NULL,
    UNIQUE(profileKey, contentId)
);

getCachedOnlineByProfileAndType:
SELECT * FROM cached_online_metadata WHERE profileKey = ? AND contentType = ?;

getCachedOnlineByProfileAndContentId:
SELECT * FROM cached_online_metadata WHERE profileKey = ? AND contentId = ?;

upsertCachedOnline:
INSERT OR REPLACE INTO cached_online_metadata VALUES ?;

deleteAllCachedOnlineForProfile:
DELETE FROM cached_online_metadata WHERE profileKey = ?;

countCachedOnlineForProfile:
SELECT COUNT(*) FROM cached_online_metadata WHERE profileKey = ?;

-- ... remaining 10 tables follow the same pattern
```

Each DAO method becomes a named query in the `.sq` file, with generated Kotlin methods on the `SubSlothDatabase` class.

- [ ] **Step 2: Rewrite UserPreferences**

Replace `DataStore<Preferences>` with `Settings`. Since `Settings` doesn't provide Flow-based observation, wrap reads in `channelFlow` or `MutableStateFlow`:

```kotlin
class UserPreferences(private val settings: Settings) {
    private val _updates = MutableSharedFlow<Unit>(extraBufferCapacity = 64)

    // Example: reading a string preference
    fun getString(key: String, default: String = ""): String =
        settings.getString(key, default)

    // Example: observing a preference (polling-based approximation)
    fun observeString(key: String, default: String = ""): Flow<String> = 
        channelFlow {
            send(settings.getString(key, default))
            // Settings doesn't have native observation; use merge with _updates
            _updates.collect { send(settings.getString(key, default)) }
        }

    suspend fun setString(key: String, value: String) {
        settings.putString(key, value)
        _updates.emit(Unit)
    }
}
```

### Risk assessment

- **High effort** — 11 tables with ~50+ queries to migrate
- Room's `Flow<List<T>>` DAO pattern maps well to SQLDelight's `.asFlow().mapToList()`
- DataStore's `edit {}` transactions don't exist in `Settings` — will need explicit transaction handling or accept eventual consistency
- CredentialStore currently uses DataStore preferences + encryption — the encryption part is out of scope for this migration; use platform-specific encrypted settings if available
- The `Settings` API is synchronous — need to wrap in coroutines for existing suspend callers
